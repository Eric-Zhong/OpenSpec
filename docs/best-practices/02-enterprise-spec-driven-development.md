## 核心要点

- 随着 AI Agent 的持续自主执行逐步替代交互式提示，**清晰地表达开发意图**变得比以往任何时候都更加重要。
- 规范驱动开发（SDD）能有效帮助工程师管理上下文，但在企业规模落地时，现有 SDD 工具仍存在若干需要理解的空白。
- 短期内，SDD 的采用需要与现有工作流集成、支持遗留项目（无规范的已有代码库），并逐步启用更高级的技术。
- 长期来看，随着我们转向以审查为中心的角色，需要培养使用 SDD 工具的直观能力，包括高效管理上下文以避免被额外反馈循环和验证所淹没。
- 当 SDD 实施得当时，它能改善各利益相关者之间的协作。仅将其视为技术流程会错失这一主要收益。

## 一、意图表达的演变：从指令到对话

过去一年中，AI 辅助编码经历了显著变化。我们从在 IDE 和聊天界面之间复制粘贴代码，进化到了使用专用的 CLI 工具和 AI 原生编辑器。

### Vibe Coding —— 指令式交互

尽管工具不断进化，但 "Vibe Coding"（与 AI 反复迭代直到代码正常工作，无需刻意的前期规划）的交互方式基本仍停留在指令层面，每次一个提示。代码实现本身成为了进一步引导的上下文。

**图 1：Vibe Coding 工作流**

![Vibe Coding Workflow](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/enterprise-spec-driven-development/en/resources/1Figure-1-1771319819572.jpg)

> 在 Vibe Coding 中，开发者逐个提示与 AI 交互，AI 直接生成代码，开发者通过运行和修改代码来引导方向。

### 规划模式 —— 更好的准备

**规划模式**（AI 在编写任何代码之前，先起草执行计划供人类审核）是 AI 编码的重要进化，它能早期发现意图对齐问题。通过要求人类和 AI 在跳入实现之前，先共同思考和确认任务列表、相关验证机制等，它延长了自主执行时间，并交付了更完整的结果。这是我们与 AI 之间的第一次 "启动会议"，它认识到：**更好的前期对话能带来更一致的结果。**

然而，人类与 AI 的交互仍然偏向战术性和指令式。由于计划通常不会在执行后保留，代码实现成为了优化和后续功能的主要上下文。

**图 2：规划模式工作流**

![Plan Mode Workflow](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/enterprise-spec-driven-development/en/resources/1Figure-2-1771319819572.jpg)

> 规划模式中，AI 先生成计划，人类审核确认后，AI 才开始执行代码编写。

### 规范驱动开发 —— 人类与 AI 的对话

规范驱动开发（SDD）的出现，是因为 AI 模型开始展现出在较长时间内持续专注于复杂任务的能力。在这种模式下，人类与 AI 之间反复的指令式交互并非最佳使用方式。同时，让 AI 独立运行很长时间又存在偏离预期结果的风险。**我们需要有效的上下文工程来确保意图对齐。** SDD 通过建立与 AI 的共同理解来解决这一需求，规范在此过程中充当人类与 AI 之间的对话媒介，而非操作手册。

**图 3：规范驱动开发高级工作流**

![SDD High-Level Workflow](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/enterprise-spec-driven-development/en/resources/1Figure-3-1771319819572.jpg)


> SDD 工作流中，规范作为人类与 AI 之间的桥梁，确保在整个开发过程中意图保持一致。

本文将探讨企业如何采用 SDD，包括需要解决的即时工具空白、与现有工作流的集成模式，以及使 SDD 在规模上可持续所需的利益相关者协作变革。

## 二、企业级采用：为何重要，以及为何它不是技术部署

SDD 已在多个技术维度上展现出清晰的价值。除了实现更长、更专注的自主执行外，它还有助于解决 token 用量和上下文窗口管理问题，实现 AI Agent 的最优和成本效益使用。

然而，SDD 最重要的影响可能是**文化层面**而非技术层面。

### 对话优于指令

当高级工程师协作时，沟通是对话式的，而非单向指令。我们通过对话达成共同理解，这种共同理解定义了我们构建什么。SDD 在人类与 AI Agent 之间促进相同的模式，Agent 帮助我们思考解决方案、质疑假设、在进入执行之前完善意图。

### 协作上下文优于更智能的模型

在概念层面，通过 SDD，团队可以将功能拆解为引导自主执行的组成部分（图 4）：

| 阶段 | 问题 | 说明 |
|------|------|------|
| **发现（Discover）** | **What** | 业务上下文定义了我们要服务的什么用例？ |
| **设计（Design）** | **How** | 技术方法如何将用例映射到我们的架构？思考模块、实现机制和通信通道 |
| **任务（Tasks）** | **Execute** | 详细执行计划，Agent 可据此行动，具有清晰的验证性和并行化机会 |

但即使这种对话式方法，当个人独立实践时，也会错失更大的机会。虽然 AI 扮演不同角色（如图 4 所示）来协助编写不同规范，但让单个开发者独自完成整个过程并无意义。

**通过跨职能规范构建执行上下文的团队，优于个人优化提示或追求更智能的模型。** SDD 可以通过将规范作为翻译层来捕捉不断演变的利益相关者对话。例如：产品团队定义 "做什么"，架构师塑造 "如何做"，工程团队帮助组织 "任务" 等。

随着构建变得更快、更便宜，瓶颈已经转移。如果我们一直忙于验证 AI 的输出，需求池就会缺乏新想法。简而言之，**仅靠审查驱动的方法在使用 AI Agent 时无法规模化。**

在这种情况下，团队需要协同运作，共同创意和解决问题，以引导 Agent 并行构建。掌握这种方法的组织可以让人类将更多时间投入战略问题解决，同时 Agent 并行处理多个工作流的实现。**这种团队级编排，而非个人效率提升，正是 SDD 对企业变得不可或缺的原因。**

### "SpecFall" / "Markdown 怪物" 的风险

鉴于这一重要的文化维度，将 SDD 视为技术部署会留下大量未开发的潜力。SDD 采用是一种需要发展的组织能力，而非单纯的技术实践安装。经历过企业敏捷采用的人应该能识别这种模式。工具和仪式容易安装，但如果没有文化转变，我们就可能面临 "SpecFall"（相当于 "Scrumerfall"）。

采用规范驱动工作流而不改变产品、架构、工程和 QA 利益相关者之间的协作方式，可能会在规范创建之初就产生层层过时的文档，形成 **"Markdown 怪物"**。关键在于将规范视为利益相关者之间的对话媒介和 AI Agent 的上下文引擎。

## 三、规模化采用 SDD 的挑战

企业中多层级、多利益相关者的现实暴露了当前 SDD 工具的若干空白。大多数流行工具存在以下一个或多个问题。

### 1. 以开发者为中心的工具

大多数 SDD 工具在 Git 仓库、代码编辑器和 CLI 中推广使用。这种定位对个人开发者来说很合理，但会阻碍跨职能协作。当规范存在于代码仓库中时，产品经理和业务分析师（本应是定义 "做什么" 的人）会面临参与障碍。

### 2. 单一仓库聚焦

当前工具通常将规范与代码保存在同一个仓库中。对于简单应用这可能可行，但企业系统很少是单一仓库。现代架构跨越微服务、共享库、基础设施仓库和平台组件。当你的功能需要跨越六个不同仓库时，规范应该放在哪里？如何跨这些边界保持一致性？工具并未给出明确答案。

### 3. 缺乏关注点分离

作为以开发者为中心方法的延伸，当前工具没有按演变速度和受众清晰分离制品。

- **架构决策**（如模式设计）和**业务上下文**（如验收标准）更具战略性，涉及不同的受众和审批流程。
- **任务列表**高度战术化，通常只有负责执行的工程师才会审核。

然而，大多数工具将所有内容放在功能特定的文件夹下，难以提取领域级视图或跨功能追踪技术演变。虽然 Agent 理论上可以提取全局视图，但问题在于：**这些生命周期截然不同的制品，是否应该一开始就放在一起？**

### 4. 不清晰的起始点

团队应该从覆盖整个应用的产品需求文档开始？还是从现有需求池中提取特定功能？大多数企业在 Jira 或 Azure DevOps 等工具中已有经过筛选的需求池，代表了数周或数月的前期提炼工作。但当前 SDD 工具未与这些系统集成。

团队能否从现有需求池中提取功能到 SDD 工作流中？如何让需求池与不断演变的规范保持同步？缺乏清晰的集成模式是希望采用 SDD 而不放弃现有工作需求和规划投资的团队面临的障碍。

### 5. 未定义的协作模式

并非所有利益相关者都参与所有阶段：

- 产品团队专注于功能定义，对技术仅有高层面的了解
- 架构师专注于系统设计和跨切面关注点
- 平台工程确保与组织标准的一致性

但当前工具未映射这些不同的参与模式。每个利益相关者的贡献何时开始和结束？他们何时知道需要审核？谁审批什么？这些协作机制缺乏清晰度会阻碍可持续的采用。

### 6. 广泛的规范风格和粒度

每个 SDD 工具对规范采用不同的方法：

| 工具 | 规范风格 | 特点 |
|------|----------|------|
| GitHub SpecKit | 结构化用户故事和验收标准 | 生成 OpenAPI 等机器可解析格式 |
| Amazon Kiro | EARS 模式 | 使用 EARS 语法编写验收标准 |
| Tessl | 内嵌测试 | 直接在规范中嵌入测试以验证对齐 |
| OpenSpec | 混合方法 | 同时维护顶层和归档的功能规范 |

规范文件组织策略也存在差异：功能级别（如 SpecKit 和 Kiro）、单个持续演变的规范，或混合方法（如 OpenSpec）。规范详尽程度也各不相同。

鉴于方法和粒度的广泛差异，选择工具和规范风格可能令人望而生畏。每个工具都会影响你的流程，这对新手团队有帮助，但如果工具的假设与你团队的实际工作方式不符，则会带来限制。

### 7. 规范到实现的对齐

虽然 SDD 的最终目标是意图到实现的对齐，但该过程涉及两个不同的转变：

1. **意图 → 规范**：通过对话和审核实现
2. **规范 → 实现**：对齐验证

**规范到实现的对齐验证**是选择 SDD 工具或方法时的关键因素，因为每种规范风格具有内在的可验证性特征。

### 8. 不清晰的遗留项目采用路径

无论是企业还是小型团队，我们都有已有代码需要维护或需要添加功能。在这种情况下，第一步应该是让 LLM 通读整个项目来创建规范？还是应该渐进式构建规范，专注于需要关注的区域？这里存在两个方面的问题：

- 当现有应用规模庞大时，让 LLM 创建规范可能会超出上下文限制。即使成功创建了规范，它可能非常庞大，从而带来审核困难。虽然通过代码回溯测试规范可能是获得一定信心的方法，但规范的核心目的是捕捉意图，而意图需要人类审核。对于现有系统的超大规范，实际审核并不现实。

虽然某些工具（如采用渐进式方法捕捉已有信息的 OpenSpec）声称面向遗留项目场景，但在规范跨仓库和项目分布的大规模场景下，这种不明确性仍是采用的障碍。

## 四、在不颠覆现有流程的情况下启用 SDD 采用

上述空白是战术障碍，而非根本性阻碍。组织可以通过先将实践适应现有工作流，然后在收益显现后逐步向更 AI 原生模式演进，来体验 SDD 的价值。

从头构建 SDD 工具可能看起来很诱人，但推广它的成本可能很高。**选择一个与你理念最接近的可扩展工具并进行定制，是从经验中学习的更实际路径。**

以下是一些解决现有工具进入壁垒的实用措施。

### 与现有产品需求池集成

大多数 SDD 工具源于以开发者为中心的环境，因此从工程团队开始是合理的。但这不应要求产品经理学习 Git 工作流。**MCP 服务器提供了实用的集成层。**

开发者可以从 Jira、Linear 或 Azure DevOps 直接拉取需求到 SDD 工作流中，同时进度更新流回需求池工具。

**需求池集成示例**

OpenSpec 具有三阶段 SDD 工作流，变更通常经历 "提案"、"应用" 和 "归档" 阶段。

**图 5-a：OpenSpec 规范驱动开发工作流**

这种简单集成尊重了产品团队已经在需求池上投入大量精力这一现实。与其在新系统中重复工作，我们直接桥接到已有需求所在的位置。

### 多仓库编排

业务上下文与技术实现细节之间的分离对于多仓库 SDD 编排至关重要。

考虑一个同时涉及前端和后端或跨越多个微服务的功能。需要建立仓库职责和集成模式，以便将工作分解为适当的部分并跨边界协调。

**图 6：通过 SDD 工作流促进产品经理、架构师和开发者协作**

![Cross-Role Collaboration](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/enterprise-spec-driven-development/en/resources/1Figure-5-b-1771319819572.jpg)

> 跨角色协作：产品经理定义业务意图，架构师设计技术方案，开发者执行实现

图 6 展示了产品经理、架构师和开发者如何通过三个阶段协作：

#### 发现阶段

产品经理与 AI 协作，阐述功能背后的业务意图（"做什么" 和 "为什么"）。这次对话发生在需求池上下文中，业务利益相关者在此操作。

#### 设计阶段

架构师与 AI 协作确定技术方法。对于跨多个仓库的功能，此阶段将父需求分解为**仓库特定的子需求**。每个子需求表示范围限定在单个仓库内的工作，具有清晰的技术边界和依赖关系。关键在于，这些子需求仍保留在需求池中，产品和工程团队可以追踪进度。

#### 任务阶段

开发者在其各自的仓库中处理每个子需求，并与 AI 协作详述实现任务。这是技术执行细节（如模式定义、模块分解等）所在的位置。这些制品属于仓库，因为它们与要修改的代码库紧密耦合。

通过这种分离，**业务上下文保留在产品看板上，技术实现细节保留在仓库中。**

重要的是，架构师不一定需要手动分解每个需求。相反，他们可以通过记录仓库边界、集成模式和架构约束来为编码 Agent 建立引导框架。由该上下文引导的 Agent 可以自动将这些指南应用于传入的需求，为每个受影响的仓库生成适当的子需求。

当需要架构重构时，原始业务需求保持稳定，而新的架构分解在不同仓库中生成不同的子需求。业务意图不变，但技术实现策略在演变。

### 角色特定的贡献

类似于架构师贡献架构指南，其他角色（如基础设施专家、性能专家和安全专业人员）也可以建立自己的上下文引导框架。每个框架捕获特定领域的约束和模式。

关键在于**配置 Agent 将这些角色特定的指南自动应用于传入的需求**，当它们成为工作项和任务时。而不是手动审核关卡，专门的 Agent 自动应用其领域专业知识，例如：

- 基础设施 Agent 添加部署约束
- 性能 Agent 标记优化需求
- 安全 Agent 识别合规要求

这为编排多个专门 Agent 奠定了基础，每个 Agent 层层叠加其指导，将业务意图转化为完整的、可执行的计划。

---

## 五、规范风格与验证

这是一个主观性较强的话题。以下是企业适用性和实用性的考量因素：

### 顶层引导能力

架构、代码组织和技术最佳实践等关注点跨越功能，影响规范详述，而不属于单个规范。对此类机制的默认支持（如 SpecKit 的 Constitution 和 Kiro 的 Steering Docs）或可扩展性来实现此目标非常重要。

### 顶层规范视图

能够提取或快速查看反映当前应用状态的规范制品有助于验证。

### 合理的粒度

虽然实现对齐很重要，但生成与实际代码几乎相同的制品可能是双刃剑。从审核负担的角度来看，保持规范 "人类可审核" 的规模很重要。庞大的数量会使详细审核变得艰巨。

更实际的做法是**优先选择促进有意义对话的规范风格**，促进与 AI 共同思考解决方案。验证虽然重要，但不应通过影响规范风格并产生抵触情绪来阻碍这一主要目标。

---

## 六、在遗留项目环境中采用 SDD

与其试图追溯性地为整个系统编写规范，**渐进式探索更为实用。** 使用 SDD 的主要原因之一是通过只向编码 Agent 提供它们需要知道的精确信息来减少上下文负担。**规范需要在变更区域附近最为细致。** 这种粒度也减少了前面提到的审核负担。

这种方法与我们在测试驱动方法中重构遗留代码时使用的技术相似。我们尽可能覆盖变更区域周围的现有逻辑，一旦信心合理，我们就有效地隔离该区域，从而帮助编码 Agent 专注于该区域，而非用更多细节污染上下文窗口。

随着时间的推移，**规范覆盖范围随着每次修改有机增长。** Bug 修复、功能添加、重构努力都成为为正在处理的代码添加规范的机会。这种有机方法自然创建了大小合理、人类可审核的上下文，专注于活跃开发区域，避免了全面 "规范化" 整个遗留系统的不切实际任务及其带来的审核负担。

---

## 七、长期方向

在 SDD 采用早期经常出现的问题是：**对于小变更或 Bug 修复，我们是否应该走规范路线？能否直接更新代码？** 随着组织向规范原生开发迈进，这个问题变得愈发重要。

答案决定了规范是保持次要文档状态还是成为一等工程表面。在成熟的 SDD 采用中，**每个变更（无论是主要功能还是次要 Bug 修复）都必须通过规范。** 这不仅仅是遵循流程，而是认识到规范是引导 Agent 执行的主要界面。这在采用 AI 原生 SDLC 时是一个重大流程转变。

历史上，我们移除了直接修改服务器代码的权限，因为这些直接更改会在下一次发布部署时被覆盖。通过移除直接服务器访问权限，团队必须在版本控制中的代码（单一事实来源）中进行修复，并将这些变更通过正确的发布管道重新部署。这种服务器访问移除确保了修复在后续发布中持久存在。

类似地，**对于 AI 生成的代码，代码问题通常是规范中存在空白的结果。** 直接在代码中的修改可能会进一步扩大这种规范差距。由于 AI 生成的非确定性，每当基于该规范重新生成代码时，这种差距会以不同形式重新出现。继续手动修补代码无法规模化，尤其是 AI 在短时间内可以生成大量代码的情况下。**向规范反馈以关闭差距更为可持续。**

因此，我们需要让 "做正确的事" 变得更轻松，在规范层面而非代码层面工作。例如，虽然代码仍然是我们版本控制和审核的制品，但其编写可能仅限于 AI 编码 Agent。

### 引导框架治理

Leigh 和 Ray 在他们的 InfoQ 文章《规范驱动开发：当架构变为可执行》中引入了 **SpecOps** 的概念，他们将规范编写确立为一等工程表面。

当规范成为工作进入系统的主要方式时，它们值得与生产代码相同的质量实践、版本控制、审核流程和持续改进。

这一转变影响深远。如果 Agent 从规范执行，那么**规范质量直接决定实现质量。** Bug 不仅仅是代码缺陷，它还是改进生成该代码的规范和引导框架的机会。这就是反馈循环变得关键的地方。

当 Bug 出现时，理解其来源至关重要：

| 差距类型 | 问题 | 解决方案 |
|----------|------|----------|
| **规范到实现差距** | 规范清晰，但实现偏离 | 加强任务完成验证机制，引导框架需要更好的验证 Agent 或更明确的实现约束 |
| **意图到规范差距** | 讨论中遗漏了用例细节，规范本身不完整 | 改进规范提取流程，在引导框架中添加问题模式、研究步骤或分析框架 |

这些问题不仅仅是 Bug 分类。**它们是我们上下文联框架的质量指标。** 每个差距揭示了框架需要改进的地方。质量工程的角色从验证实现演变为**验证和改进引导 Agent 执行的框架。**

通过将规范编写视为具有反馈循环、质量指标和持续改进的运营纪律，单个功能需要的更少手动调整。框架将积累的见识向前传递。

## 八、实现对齐的务实路径

没有意图、规范和实现之间的完美对齐，质疑 SDD 的价值是合理的。虽然可以工程设计利用规范独立测试实现的验证机制，但可实现的对齐程度因规范类型而异。从一开始就优化完美对齐可能使规范过于细致，导致审核疲劳并削弱采用。

从务实角度看，即使在人类团队成员之间，我们也面临对齐问题。在人类层面，我们通过减少未来沟通错误的机制来解决这些问题。同样，**回顾式反馈循环有助于随时间改进对齐。** 每个识别出的差距加强了框架，使未来的规范更完整，实现更对齐。

这一转变代表了 Agent 编排开发中质量工作的根本性转变。**质量专员从审核完成的实现转变为验证上下文引导框架**，它们编码的约束以及这些验证机制是否能早期捕获偏差。角色从实现质量转变为框架质量。

## 九、结语

随着具备持续自主执行能力的 AI Agent，软件交付的瓶颈已经转移。问题不再是我们能以多快的速度编写代码，而是**我们能多有效地表达意图。** 正如 Adrian Cockcroft 在 QCon SF 上所描述的那样，我们正学会引导 Agent 集群。这种构建方式是与管理个人贡献者截然不同的组织能力。

SDD 促成了这一转变，但前提是我们要认识到实际发生的变化：

| 角色 | 转变 |
|------|------|
| **产品团队** | 需要清晰阐述业务上下文，使 Agent 能理解用户价值和验收标准 |
| **架构师** | 必须将技术约束和集成模式编码为可重用的引导框架 |
| **工程师** | 从编写实现转变为验证 Agent 生成的代码是否与规范对齐 |
| **质量专员** | 从测试完成的实现转变为确保上下文引导框架本身是健全的 |

通过 SDD，对话不再仅限于人类之间。**规范成为产品、架构、工程和质量的共享界面，协作构建由 AI Agent 转化为行动的执行上下文。** 规范编写中的反馈循环正是这种协作发生的地方。

将 SDD 视为技术部署的人将获得技术收益，如更好的 token 使用、更长的 Agent 运行时间和更少的幻觉。而将其视为组织转型的人将解锁有效引导 Agent 集群的能力，让人类创造力专注于战略问题解决，同时 Agent 处理多个工作流的实现。

**这一转型不是未来状态，而是对于准备做出转变的组织而言，现在即可实现。**

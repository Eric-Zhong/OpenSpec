## 什么是遗留项目（Brownfield Project）？

"遗留代码" 有许多定义，我认为 Michael Feathers 在其著作《与遗留代码高效协作》中给出的定义最发人深省：**任何没有测试的代码，本质上都是遗留代码。**

类似地，在规范驱动开发（SDD）的语境中，**"遗留项目" 可以定义为那些并非基于规范构建的项目。** 我们唯一可用的制品就是实现本身——即代码。

---

## 能否逆向工程规范？

理论上，我们可以逆向工程规范。一种快速实现方式是使用类似 **Repomix** 的工具将代码打包为更小的格式，然后连同我们使用的 SDD 工具的上下文一起交给 LLM，从而生成整体规范。

然而在实践中，**AI 生成的规范往往不准确。** 模型无法完全捕获原始开发者的意图或代码中嵌入的微妙细节。结果是，规范表面上看起来合理，但实际上与现实存在偏差。**这样的规范无法作为未来开发的可信赖基础。**

### 逆向工程的问题

逆向工程规范本身可能相当复杂。即使我们做到了，审核生成的规范也可能不切实际。

在测试驱动开发（TDD）的语境中，当处理没有测试的遗留代码时，我们应该先编写所有测试吗？**那是不切实际的。** 在 Feathers 的工作中，采用的方法主要是在代码变更区域周围编写测试，首先建立当前行为（特征测试），然后在此基础上测试驱动其余代码。

**同样，对于遗留项目，渐进式编写规范要实际得多。**

还存在 **对齐丢失** 的问题。逆向工程的规范是派生制品。当新功能基于未对齐的规范开发时，回归和意外副作用的风险急剧上升，因为规范不再真实反映系统的实际状态。

---

## 为什么渐进式方法更好

渐进式方法将规范聚焦于**单个即将发生的变更**，而非试图一次性捕获整个代码库。在进行修改之前，仅为即将变更的区域编写规范。这更加经济：**范围有限、上下文新鲜、生成的规范准确反映意图。**

随着时间的推移，这种实践产生复利效应。每次变更都会留下一个覆盖其系统切片的规范。**随着规范密度在频繁触及的区域增长，这些区域开始表现得像新项目（Greenfield）一样。** 覆盖范围在最需要的地方自然增长。

> 如需深入了解此方法在企业规模的应用，请参阅 [InfoQ 上的《企业级规范驱动开发》](https://www.infoq.com/articles/enterprise-spec-driven-development)。

## 在遗留项目中与 OpenSpec 实践规范驱动开发

### 使用自定义配置与"探索 → 继续"工作流

在遗留项目中应用 SDD 时，**推荐使用自定义 OpenSpec 配置而非默认的 `propose` 命令。** 如需了解自定义配置的更多信息，请参阅 [OpenSpec 1.2 版本博客](https://openspec.pro/)。

**遗留项目的推荐工作流：**

| 步骤 | 命令 | 说明 |
|------|------|------|
| 1 | `/opsx:explore` | 在编写任何规范之前，探索变更并理解代码库 |
| 2 | 审核探索输出 | 确认 AI 对代码库的理解准确 |
| 3 | `/opsx:continue` | 逐步推进提案、规范、设计和任务 |

在遗留项目中，**逐个审核每个制品能让您更好地控制生成内容**，从而确保规范扎根于实际代码库。

### 在探索阶段通过 Repomix MCP 传递代码库上下文

在探索阶段，使用 **Repomix MCP** 传递现有代码库的上下文。这教育 AI 了解遗留代码库，使生成的制品反映实际系统而非假设。

**示例命令：**

```
/opsx:explore I would like to remove the maybe option in RSVP, use repomix mcp to understand existing code
```

Repomix 将代码库打包为 AI 可直接消费的格式，**让探索阶段准确扎根于已存在的代码。**

对于大型代码库，Repomix 等工具在管理上下文窗口使用方面特别有帮助。

## 结语

渐进式方法为您提供**控制、准确性和渐进式增长的覆盖范围**，无需在逆向工程可能不成立的规范上进行大量前期投入。您从工作所在处开始，构建反映真实意图的规范，让遗留项目随时间逐步转型。

# OpenSpec 工作流指南

OpenSpec 遵循一套轻量级、可迭代的工作流，帮助你在编写任何代码之前，先与 AI 助手明确"要做什么"以及"为什么做"。本文档将带你逐步走完整个流程。

## 工作流总览

OpenSpec 工作流包含四个核心阶段：

1. **提案（Proposal）** — 明确你要构建什么、为什么要构建
2. **规划（Planning）** — 生成规范、设计方案和任务清单
3. **实施（Implementation）** — 按照规范逐步实现功能
4. **归档（Archive）** — 将阶段性知识整合为项目持久资产

```
    ┌──────────┐     ┌──────────┐     ┌─────────────┐     ┌─────────┐
    │  1 提案   │ ──→ │  2 规划   │ ──→ │  3  实施   │ ──→ │  4 归档  │
    │ /opsx:new │     │ /opsx:ff  │     │ /opsx:apply │     │/opsx:archive│
    └──────────┘     └──────────┘     └─────────────┘     └─────────┘
```

---

## 第一步：创建提案

使用 `/opsx:new` 命令创建一个新的变更提案：

```bash
/opsx:new add-dark-mode
```

### 会发生什么

- OpenSpec 会创建一个新的变更目录 `openspec/changes/add-dark-mode/`
- 自动初始化目录结构
- 准备提案文档

### 提案文档（proposal.md）

提案文档需要回答以下关键问题：

| 要素 | 说明 |
|------|------|
| **Why（为什么做）** | 变更的动机与业务价值 |
| **What（做什么）** | 哪些内容会改变，哪些保持不变 |
| **Scope（范围边界）** | 功能的边界与限制条件 |
| **Success Criteria（成功标准）** | 如何判断功能已完成 |

> **提示**：提案阶段即可审查，无需等待代码。这是你在投入开发之前发现需求偏差的最佳时机。

---

## 第二步：生成规划文档

使用快速推进命令一次性生成所有规划文档：

```bash
/opsx:ff   # "fast-forward" 快捷方式
```

### 生成的文档清单

| 文档 | 用途 |
|------|------|
| `proposal.md` | 变更动机与范围定义，回答"为什么做"和"做什么" |
| `specs/` | 按能力组织的功能与非功能需求，包含验收场景 |
| `design.md` | 技术方案与架构决策，记录实现策略与权衡考量 |
| `tasks.md` | 按依赖关系排序的实施检查清单，拆分为可执行的任务 |

### 实施前审查（关键步骤）

在继续之前，逐项检查以下问题：

- [ ] 提案是否与目标一致？
- [ ] 规范是否完整、准确？
- [ ] 设计方案是否符合当前架构？
- [ ] 任务清单是否清晰、可执行？

> **提示**：OpenSpec 生成的规范文档非常精简（约 250 行），相比之下其他工具通常会产生约 800 行。更少的篇幅意味着更快的审查速度和更高的聚焦度。

---

## 第三步：实施

确认规划文档无误后，开始实施：

```bash
/opsx:apply
```

### 工作流程

你的 AI 助手将按以下步骤执行：

1. 读取 `tasks.md` 中的任务清单
2. 遵循 `design.md` 中的设计方案
3. 逐项完成任务
4. 随工作进展同步更新任务状态
5. 对照规范验证实现结果

### 核心优势

| 特性 | 说明 |
|------|------|
| **确定性** | 相同的规范产生一致的结果 |
| **可审查** | 实施前即可看到将要构建的内容 |
| **高聚焦** | 干扰少，执行效率高 |
| **可追溯** | 每一处变更均可追溯到对应的规范 |

> **提示**：得益于规范的精简设计和较少的任务数量，OpenSpec 的实施阶段明显快于其他工具。

---

## 第四步：归档与知识整合

实施完成并通过测试后，执行归档操作：

```bash
/opsx:archive
```

### 会发生什么

- 将变更从 `changes/` 移动至 `changes/archive/`
- 将阶段性知识整合为持久化规范
- 更新 `openspec/specs/` 下的主规范文档
- 同步更新 OpenSpec 仪表板

### 知识整合的价值

归档操作将临时变更文档转化为项目的持久知识：

- **规范成为项目知识库的一部分** — 不再散落在聊天记录中
- **后续变更可以引用历史工作** — 避免重复决策
- **新成员可快速理解系统架构** — 降低上手门槛
- **上下文超越对话会话持久存在** — 重启对话不丢失信息

> **提示**：`AGENTS.md` 文件会提醒 AI 助手在开始新任务前查阅已整合的规范。

## 工作流核心原则

| 原则 | 说明 |
|------|------|
| **灵活而非僵化** | 随时更新任意文档，无硬性阶段壁垒。自由迭代，随时调整。 |
| **迭代而非瀑布** | 以小步变更推进：审查 → 实施 → 归档 → 循环。告别"大爆炸"式发布。 |
| **简单而非复杂** | 命令简洁、结构清晰。5 分钟内即可上手，无需冗长的学习周期。 |
| **适配存量代码** | 专为已有代码库设计，无缝对接遗留系统。无需从零开始。 |
| **可伸缩** | 从个人项目到企业团队，同一工作流、不同规模。 |

## 最佳实践

### 开始前

- 清空上下文窗口，以获得更好的 AI 输出质量
- 使用高推理能力模型（如 Opus 4.5、GPT 5.2）
- 从小变更开始，熟悉工作流后再处理复杂需求

### 开发过程中

- 实施前务必审查提案和规范
- 随着认知加深，及时更新文档（记住：灵活而非僵化）
- 保持 `tasks.md` 与实际进度同步

### 完成后

- 充分测试后再归档
- 审查整合后的规范，确保知识完整保留
- 将归档规范作为未来工作的参考依据

# 规范驱动开发：当架构变得可执行

> **原文作者：** Leigh Griffin（Red Hat 高级工程师经理）, Ray Carroll（Red Hat 高级首席软件工程师）
> **发布日期：** 2026 年 1 月 12 日（约 20 分钟阅读）
> **来源：** [InfoQ - Spec Driven Development: When Architecture Becomes Executable](https://www.infoq.com/articles/spec-driven-development)

---

## 核心要点

- **规范驱动开发（SDD）** 代表了第五代编程范式转变，将抽象提升到系统层级。工程师以声明式方式定义意图，平台通过生成和验证机制将意图转化为可执行系统。
- **架构不再是建议性的**，而是可执行且可强制的。规范现在定义系统事实，代码则持续生成、验证和重新生成。
- **漂移检测** 将架构从设计时制品转变为自我监控的控制系统，通过持续的模式验证、契约测试、负载检查和规范差异分析来实现。
- **人类权威向上转移**，从实现层转移到意图、策略和伦理层。SDD 并未将人类排除在外，而是将其责任重新定位到最高抽象层。
- SDD 提供架构确定性、减少系统性漂移和多语言一致性，但也引入了新的复杂度表面和工程师的认知转变。

## 一、第五代抽象的崛起

软件工程的每一次重大转变都由一个一致的力量驱动：**抽象的提升**。

最早的软件以机器码编写，随后汇编语言引入了可读性和控制层。高级语言经历了多个不同范式，催生了 C、Java、Python 等通用语言及其衍生语言。这些语言推动了抽象的进步，将内存管理和平台特定细节从日常工作中隐藏，由系统在后台处理。这种可访问性水平推动了更广泛生态系统的成长，每一代新兴语言都伴随着互补工具链的演变。

**图 1：编程语言代际演变**

![编程语言代际](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/spec-driven-development/en/resources/171figure-1-1767777705864.jpg)

> 从机器码到自然语言的编程演变路径

**第五代：自然语言编程**

第五代编程——使用自然语言编程——长期以来一直是编程语言演进的靶心：人类使用母语交流，系统以可执行方式解释。直到最近，这一演进才真正进入主流。推动这一进程的是**生成式 AI 的能力**，它现已成熟到可以将人类输入转化为您选择的编程语言解决方案。这一演进场景在数十年的学术研究和博客讨论中有所记载。

**开发者角色的演变**

这些转变中的共同主题是开发者角色的演变。每次抽象提升都让开发者更专注于意图而非机制，我们现在已进入另一个转折点。第五代不仅因生成式 AI 的广泛使用而加速，还与行业主导的采用同步发生。这代表了开发者如何根本性接近其工作的新纪元。

与之前几代成熟的情况类似，支持它的工具链也已出现。在之前的几代中，工具在稳定期后出现；然而，随着 AI 研究和输出的 rapid 进展，**工具链现在有可能塑造和定义这一代，而不仅仅是支持它。**

在这一进程中，一套专注于**规范驱动开发（SDD）** 的关键工具已经出现。这一趋势得益于 AI 辅助代码生成的接受，它允许开发者提升自身的抽象层级，表达系统应该做什么，而智能工具则将实现方式具象化。

这一转变重新定义了我們如何接近系统的架构和设计。现在，团队不再维护随时间漂移的静态架构图，而是维护**活的规范**。这些规范定义系统契约、边界、不变量和行为。此类规范天生可执行：它们可以生成代码、文档、SDK、模拟甚至服务基础设施。AI Agent 通过**角色映射**（将角色的专业知识捕获为 Agent 可消费的输入）为其上下文播种，现在可以在整个管道中作为解释器、验证者和领域特定协作者权威性地行动。

本文将 SDD 作为架构范式进行探讨，详细说明规范如何成为系统的可执行骨干，漂移检测和持续验证如何将架构转变为运行时不变量，AI 和 Agent 工具如何重塑生成和治理，以及这一模型如何代表软件抽象漫长演变中的下一个重大转折点。

## 二、SDD 的架构

"规范驱动开发" 这一名称可能暗示一种方法论，类似于测试驱动开发（TDD）。然而，这种框架低估了其重要性。**SDD 更准确地被理解为一种架构模式**，它通过提升可执行规范高于代码本身，反转了传统的事实来源。

SDD 代表了软件系统架构、治理和演进方式的根本性转变。在技术层面，它引入了一个**声明式、契约中心的控制平面**，将规范重新定位为系统的主要可执行制品。相比之下，实现代码成为架构意图的次要、生成表示。

传统架构依赖源代码作为规范控制表面。在 SDD 中，该控制表面上移至**规范控制平面**。此控制平面正式允许我们定义以下制品：

| 制品类型 | 说明 |
|------|--|--|
| 接口契约 | 能力、输入/输出、行为保证 |
| 数据模式与不变量 | 结构、约束、验证规则 |
| 事件拓扑 | 允许的流、排序、传播语义 |
| 安全边界 | 身份、信任区域、策略强制 |
| 兼容性规则 | 向后和向前兼容 |
| 版本语义 | 演进、弃用、迁移 |
| 资源与性能约束 | 延迟、吞吐量、成本 |

这一变更涵盖了行为与治理的经典架构表面，并带有正确性的时间维度。SDD 将这些领域集中到一个单一权威模型中，而非跨服务和仓库独立协调。**这种模式更接近语言类型系统或编译器：它不执行程序本身，而是定义什么可表达、拒绝什么无效、并约束演进以保持正确性和兼容性。** 架构不再是建议性的；它变得可强制和可执行。

**图 2：SDD 五层执行模型**

![SDD 五层执行模型](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/spec-driven-development/en/resources/132figure-2-1767777705864.jpg)

> SDD 的五层架构：规范层 → 生成层 → 制品层 → 验证层 → 运行时层

尽管标有 SDD 品牌的工具日益可见，但从根本上说，它不是产品、框架或形式语言。**它是一种架构构造**，以惊人的一致性重新出现为**五层执行模型**。

这些层共同形成一个封闭的、规范治理的控制系统，其中意图持续塑造执行，执行持续验证意图。由此产生的不是对现有架构的渐进式改进，而是**权威、控制和事实所在地的根本性倒转。**

让我们现在检查这五层。我们将以一个简化的订单管理服务的示例来展示层间的进展以及它们如何相互强化。

### 1. 规范层

这是系统行为的权威定义。它捕获系统**是什么**的声明式意图，而非**如何实现**。这一层通常包含 API 模型、消息契约、领域模式和系统特定的策略中心约束。从抽象角度来看，它既人类可读又机器可执行，同时作为设计制品和操作控制表面。

以我们的订单管理服务为例，在规范层中，我们声明什么必须为真，而非如何实现：

```yaml
service: Orders
api:
  POST /orders:
    request:
      Order:
        id: uuid
        quantity: int > 0
    responses:
      201: OrderAccepted
      400: ValidationError

policies:
  compatibility: backward-only
  security:
    auth: mTLS
```

此规范直接陈述我们的期望：
- 订单必须具有正数量
- API 不得引入破坏性变更
- 请求必须经过身份验证

**此处未引用任何语言、框架或基础设施。**

### 2. 生成层

这一层将声明式系统意图转换为可执行形式。它作为**多目标系统编译器**运作，但与发出机器指令的经典编译器不同，这一层发出跨语言、框架和平台的**系统形状和可强制运行时表面**。在此，问题空间由规范层声明，工具将其操作形式具象化。典型输出包括类型模型、契约存根、验证中间件、文档以及一系列集成和一致性测试。

以订单示例为例，规范被摄入并发出可强制的系统表面：

```
spec.yaml
  → 类型模型（Java, TypeScript）
  → 请求验证器
  → API 存根
  → 契约测试
```

工具将声明意图转换为具体的、可强制的形式。

### 3. 制品层

这一层包含生成阶段的**具体输出**：生成的服务、组件、客户端、数据模型和适配器。关键在于，这些制品不被视为主要资产。相反，它们是**可重新生成、可丢弃、可替换和持续可调和的**。这反转了传统软件架构的一个基本假设：**代码不再是系统记录；规范是。** 随着代码变得无限可重现并按需生成，新兴术语 **"Ambient Code"（环境代码）** 恰当地捕获了这一范式转变。

我们的订单形状现在准备以生成的、可丢弃的代码具象化：

```typescript
// 类型模型
export interface Order {
  id: string;
  quantity: number;
}

// 验证器
if (order.quantity <= 0) {
  throw new ValidationError("quantity must be greater than zero");
}
```

这些制品不是事实来源。如果规范变更，它们会被重新生成。如果被删除，不会丢失任何内容。

### 4. 验证层

这一层强制**意图与执行之间的持续对齐**。它由契约测试、模式验证、负载检查、向后兼容性分析和架构漂移检测机制组成。它扮演与编程语言类型系统和虚拟机监控程序相同的结构角色：**主动防止架构违规传播到运行时。**

由生成层创建的制品最终在此受到治理，验证确保运行时不会从意图漂移：

```
✓ 拒绝 quantity <= 0 的请求
```

违规在构建时、部署期间和 CI 系统中被检测。**架构正确性被持续强制，而非手动审核。**

### 5. 运行时层

这是**操作系统本身**，由典型的制品混合组成：

- API
- 消息代理和流管道
- 函数、方法和等效构造
- 集成服务

关键在于，**运行时的形状完全受上游规范和验证层约束。** 结果，运行时行为变得**架构确定性的**而非涌现的。

如果我们尝试使用负数量的订单服务：

```json
POST /orders
{
  "id": "123",
  "quantity": -1
}
```

我们返回 `400 ValidationError`，不是因为运行时拒绝了请求，而是因为**行为在规范层声明，由生成层具象化，由制品层实例化，并由验证层持续强制**，远在系统执行任何请求之前。

## 三、架构倒转

数十年来，软件架构在一个 largely 未受挑战的假设下运作：**代码是最终权威。** 架构图、设计文档、接口契约和需求规范都存在以指导实现。然而，运行系统始终从其最终部署的内容派生其事实。当出现不匹配时，标准响应是 **"更新文档"**。

**SDD 完全反转了这一关系。** 规范成为系统现实的权威定义，实现持续派生、验证，并在必要时重新生成以符合该事实。这不仅仅是哲学区别；它是**软件系统治理的结构倒转。**

**图 3：传统软件交付管道**

![传统管道](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/spec-driven-development/en/resources/112figure-3-1767777705864.jpg)

> 线性、有损的传统交付管道

传统软件交付遵循线性、有损的管道（如图 3 所示）。每次翻译步骤引入重新解释、手动适应和隐藏假设。**架构漂移因此未被防止；它在后期被发现**，通常通过生产事故、失败的集成、安全审计或合规违规。当检测到不对齐时，它是法医式的而非纠正性的。

**图 4：SDD 治理的软件交付管道**

![SDD 治理管道](https://imgopt.infoq.com/fit-in/3000x4000/filters:quality(85)/filters:no_upscale()/articles/spec-driven-development/en/resources/78figure-4-1767777705864.jpg)

> 闭环控制的 SDD 交付管道

SDD 根本性地将此流重构为**受治理的控制循环**。此控制循环用**主动架构强制**替换延迟发现。漂移检测不修补运行时行为；它**纠正规范权威并触发系统的受控重新生成。** 传统架构假设代码随时间成为事实；SDD 通过确保规范保持永久事实来源，且运行时持续符合它来反转这一点。

**架构倒转总结：**

| 经典模型 | SDD 模型 |
|------|--|--|
| 代码定义行为 | 规范定义行为 |
| 架构是建议性的 | 架构是可执行且可强制的 |
| 漂移在事后发现（或完全被忽略） | 漂移在运行前防止并持续监控 |
| 实现定义事实 | 规范定义事实 |
| 验证是回顾性的 | 验证是持续且系统性的 |
| 运行时是涌现的 | 运行时是架构确定性的 |

在 SDD 中，**代码不再是事实涌现的地方，而是事实实现的地方。**

这一倒转在结构上等同于先前的范式转变，其中整类正确性约束从人类责任中移除并变得机械可强制：

| 转变 | 说明 |
|------|--|--|
| 从手动内存管理到垃圾回收 | 内存安全成为运行时不变量 |
| 从裸机到虚拟机 | 隔离和资源边界成为平台保证 |
| 从物理服务器到声明式基础设施 | 配置漂移和拓扑正确性持续调和 |
| 从非类型语言到静态类型系统 | 结构正确性在编译时强制 |
| 从非正式接口协议到模式和契约强制的 API | 交互正确性机械验证 |

在每个案例中，**正确性从人类惯例强制转变为平台结构强制。** SDD 将同一原则应用于系统边界、架构和行为本身。

## 四、漂移检测：使架构自我强制

一旦规范成为权威，漂移检测就不再是测试便利；它成为**强制性的架构能力**。它是将意图转化为不变量的强制机制。在此模型中，漂移不仅仅是模式不匹配；它是**声明的系统意图与观察到的系统行为之间的任何偏差。** 该偏差可能是结构性的、行为性的、语义性的、安全相关的或演化性的。我们在实验中遇到的一些示例包括：

- API 返回规范中未声明的字段
- 服务在重构期间静默省略必需字段
- 消息负载在没有协调模式版本的情况下演进
- 错误处理偏离契约保证
- 安全范围相对于原始策略意图退化

**没有漂移检测，SDD 退化为文档驱动开发。** 有了它，系统变得自我监控。漂移检测形成**闭环反馈控制系统**。它持续比较系统声称做什么与实际做什么。这与仅提供周期性、基于样本保证的经典测试根本不同。

在传统架构中，意图的偏差静默传播，通常持续数月，直到它们表现为停机、审计失败或安全违规。在 SDD 系统中，**漂移默认成为机器可检测的。** 规范验证器可以直接嵌入 CI 管道，运行时强制层（模式验证、负载检查、契约验证和规范差异引擎）都成为一等架构组件。当输出违反规范时，系统快速失败并允许纠正。

**图 5：漂移检测反馈循环**

![漂移检测](https://www.infoq.com/articles/spec-driven-development/)

> 漂移检测如何将架构转变为运行时不变量

此强制要求在本质上多模型的未来变得更加关键。软件系统将越来越多地由**人类驱动的开发和机器驱动的生成**塑造，通常在同一规范表面上并发运作。系统中不再存在单一线性路径。变更可能源自开发者、AI Agent、自动重构工具或策略驱动的生成器。**这种演化路径的多样性显著放大了漂移问题：偏差不再是边缘情况；它是必须持续治理的自然状态。**

净效果是治理的深刻转变。**架构不再是设计阶段制品；它成为持续强制的运行时不变量。** 规范从被动参考资料转变为主动控制表面，漂移检测作为保持系统与意图对齐的反馈信号。

然而，这并不意味着机器单方面定义正确性的完全自主系统。**规范不仅仅是机械契约；它是人类对目的、风险容忍度和权衡的表达。** 漂移检测可以识别系统已偏离，但它不能单独决定该偏差是否可接受、偶然或可取的。一些漂移代表缺陷，而其他漂移代表演进。**在这一边界——自动强制与解释性判断相遇之处——人类的角色再次变得关键。** 不是作为失败后的被动日志审核者，而是作为治理意义、意图和受控变更的主动参与者。这就是 **Human-in-the-Loop（人在环路）** 成为不仅安全网而是一等设计原则的地方。

## 五、人在环路：在自动化架构中保留意图

当我们首次探索这种系统设计模式时，我们以天真的 "Vibe Coding" 心态接近它，接受生成的变更而阻力最小，信任 SDD 工具链为我们处理边缘情况。该假设迅速失败。**取而代之的是一个更强大的认识：SDD 并未将人类排除在环路外；它将人类判断重新定位到更高的控制平面。** 问题不再是人类如何实现系统，而是他们如何以及在哪里治理系统。

SDD 并未消除人类在软件设计中的参与。它**重新分配人类认知应用的地点。** 传统上，一旦功能实现，开发者将大部分精力用于解析不匹配、调试集成失败、调和分歧服务和修复变更的意外副作用。随着时间推移，这错误地与软件工程工艺等同。实际上，它是**维护大型、长期、面向生产的系统的负担。** SDD 将此负担转移到机器，同时刻意保留人类对意图、策略和意义的权威。

这引入了**新型人类控制表面。** 人类仍然是领域语义、风险容忍度、安全包络和系统演化方向的最终监护人。此权威还延伸到隐含塑造工程决策的**法律、伦理和道德框架。** 这些维度无法仅从执行跟踪或行为观察中推断。它们存在于机器无法完全拥有的抽象层级。

相反，人类将这些约束明确编码到**规范层**，机器承担强制、生成和持续一致性的责任。这反映了我们工艺的历史演变：正如我们曾经将手动内存管理让位于垃圾回收，我们现在将结构强制和机械一致性委托给 SDD。**取代该委托的不是盲目自动化，而是显式审批边界：**

| 变更类型 | 要求 |
|------|--|--|
| 破坏性模式变更 | 需要人类审批 |
| 策略转变 | 需要人类授权 |
| AI 建议的重构 | 需要人类确认 |
| 兼容性降级 | 需要人类证明 |

**SDD 因此实现有界自主，而非完全自动化**，在这些边界内，长期架构意图得到保留。

通过强制漂移检测和人类监督意图，SDD 建立了人与机器之间**新的责任分工**。强制变得自动化。意义保持人类。这一分离不是哲学性的；它是架构性的，正是这一分工产生了**新一代基础系统能力。** 规范原生系统现在必须将强制、演进、验证和治理直接编码到其核心原语中。我们接下来探讨这些能力以及为什么它们在结构上区别于经典软件架构中的能力。

---

## 六、规范原生系统的核心能力

SDD 并非由单一工具、框架或平台启用。它从一组紧密耦合的架构能力中涌现，这些能力共同允许规范在规模上变得可执行、可强制和可演进。**当任何这些能力缺失时，SDD 退化为文档驱动开发或临时代码生成。** 要从理论进入操作范式，系统必须内化五种核心能力：

1. **规范编写作为一等工程表面**
2. **形式验证和类型强制**
3. **确定性生成和组合**
4. **持续一致性和漂移强制**
5. **受治理的演进和兼容性控制**

我们将此操作纪律称为 **SpecOps（规范运营）**。从 SpecOps 的角度来看，规范被视为一等、可执行的系统资产，这些能力不定义产品类别；它们代表**软件意图的控制平面。** 在规范原生系统中，规范编写不是先于实现的活动；**它就是实现活动。** 系统因此必须支持**多模型规范**，其中结构、行为和策略定义在统一模式空间中共存。这需要**可组合领域建模**，以便分层规范成为可行的架构策略而非文档便利。

随着规范成为主要系统制品，它们必须与源代码受到相同的操作严格性：**版本控制、同行评审、分支和受控合并策略都成为强制性的。** 这是规范从描述性变为**系统本身的可编程模型**的时刻。

一旦规范可执行，它还必须以与编译器前端或类型系统相同的严格性进行**机器验证。** 此强制跨越结构验证、语义连贯性和领域不变量强制。条件约束、引用完整性和跨规范一致性必须可证明。效果不仅仅是改进正确性，而是**从可表示空间中消除整类系统失败**，正如静态类型约束非法程序的方式。

在此范式中，**生成不是脚手架的形式。它是声明系统事实的具象化。** 这需要严格的确定性行为。生产级规范原生系统必须保证**输入确定性**：相同规范必须始终产生相同制品。它必须是**目标无关的**，跨语言、平台和运行时环境产生一致输出。最关键的是，**生成必须是逻辑可逆的。** 系统必须始终能够回答一个简单但基础的问题：**哪个规范状态产生了此行为？** 这种决策谱系的可追溯性是将生成从生产力辅助提升到架构权威的关键。

一旦生成自动化，**强制必然成为持续的。** 运行时系统不能再静默地从声明意图偏离。实现不能引入未记录的行为。消费者不能依赖未定义的属性。因此，架构从设计时断言转变为**运行时不变量**，由系统本身主动维护。

SDD 中最困难的能力不是生成或验证，而是**无断裂变更。** 规范原生系统必须自动将变更分类为**添加性、兼容性、破坏性或模糊性**，并强制显式兼容性策略。这引入了**受治理演进**的形式概念：并行版本表面、已知兼容窗口、受控弃用曲线和破坏性变更的显式审批门是必需的。没有它，SDD 变得架构脆弱。有了它，系统可以在不违反自身正确性保证的情况下演进。

**这五种能力引入的最深刻转变不是技术性的；它是结构性的。**

**交付单元不再是服务或代码库。交付单元成为规范本身。** 这将输出与结果重新对齐：声明什么就是交付什么。这与 vibe 驱动的、生成式编码方法形成直接对比，其中偏差是创造力（或幻觉）的涌现属性，而非受治理的设计行为。

## 七、结论：工程权衡与挑战存在

软件工程的每一次重大抽象飞跃都带来了非凡的生产力增益，同时引入了全新的系统性风险类。垃圾回收消除了大量内存错误，同时引入了暂停时间行为和新故障模式。虚拟机简化了部署，同时创建了编排复杂性。云平台移除了基础设施负担，同时引入了深层操作耦合。**规范驱动开发也不例外。**

通过将系统的事实来源提升到规范和生成器中，**SDD 并未移除复杂性；它只是重新定位了它。** 下面的权衡定义了我们在此范式规模化采用过程中经历的实际工程成本。

### 1. 规范成为主要复杂度表面

在 SDD 中，规范不再是文档制品，而是**长期的可执行基础设施。** 结果，它们获得了传统上与源代码相关的属性。它们继承了通常与源代码相关的所有属性：**技术债务、跨团队耦合、兼容性惯性和架构引力。** 因此，**模式工程成为一等架构学科**，与数据建模和分布式系统设计同等重要。

### 2. 生成器信任成为供应链问题

在 SDD 中，AI 代码生成器不再是开发者便利。它们成为**系统可信计算基础的结构组件。** 确定性、可重现性、可审计性、沙盒执行和可验证出处不再是可选属性；它们是强制性的。**代码生成从工具提升到关键基础设施。**

### 3. 运行时强制有真实成本

SDD 将强制从社会流程转移到技术控制。该转移强大，但并非免费。**运行时契约验证引入真实的计算开销。** 在小规模上，此成本可忽略。在大规模上，我们需要面对系统的目的——无论是高频 API、实时流还是延迟敏感系统。**这成为显式的架构预算项。** 正确性成为计量的资源，而非默认免费的属性。

### 4. 认知转变非平凡

SDD 用**契约优先推理**替换实现优先思维。这要求工程师采用新的心理模型：

| 传统思维 | SDD 思维 |
|------|--|--
| 思考行为 | 思考不变量 |
| 推理功能 | 推理兼容性 |
| 过程式表达意图 | 声明式表达意图 |
| 将模式视为文档 | 将模式视为可执行程序 |

**每次历史抽象飞跃都扩大了人类杠杆，同时引入了需要多年掌握的不熟悉故障模式。** SDD 现在正进入相同的成熟曲线。

---

## 架构权威的代价

虽然新的范式转变通常令人兴奋，但采用它的决策最终取决于平衡所涉及的实际权衡。

**一方面，SDD 提供：**
- 架构确定性
- 持续正确性强制
- 系统性减少漂移
- 多语言一致性
- 可重现的系统边界

**但它收取以下代价：**
- 模式复杂度
- 生成器信任要求
- 运行时验证成本
- 长期兼容性负担
- 工程角色的认知转变

**这不是避免 SDD 的理由。这是谨慎采用的理由**，带有显式治理、纪律化的规范实践和对其成本的清醒认识。**每次抽象飞跃都要求新形式的严格性。**

**SDD 只是将该严格性重新定位到它始终属于的地方：系统事实本身的定义。**
